# CO-META
Ontology for Combinatory Optimization Metaheuristics.

CO-META describes metaheuristics as networks of interconnected components (generation, selection, crossover, acceptance, stopping criteria...) with their parameters and data structures, and optimization problems through their formulation: input data, decision variables, objectives and constraints. It is written in OWL 2 DL, so it can be checked and queried with standard reasoners.

Documentation: <https://w3id.org/ontologies-ULL/CO-META>

## Repository structure
- `CO-META.ttl`: the ontology.
- `individuals/algorithms/`, `individuals/problems/`: descriptions of specific metaheuristics and problems, one file each, that import the ontology.
- `imports/`: modules with the terms reused from external vocabularies.
- `SHACL/`: shapes that check what OWL cannot, such as required values or parameter values within their bounds.
- `tests/`: test cases for the ontology and the shapes.
- `scripts/`: validation and maintenance scripts.
- `supplementary/`: supplementary material, including SPARQL queries over the ontology and its individuals. The queries rely on inferred facts, so run them on the ontology and the individuals after reasoning (e.g. with a reasoner in Protégé).
- `docs/`: documentation generated by Widoco. Do not edit it by hand.

## Modelling conventions

### General
- Describe each metaheuristic or problem in its own file, with its own ontology IRI and importing `https://w3id.org/ontologies-ULL/CO-META`.
- All individuals share the CO-META namespace, so prefix their names with the metaheuristic or problem they belong to (`ACO_pheromones`, `TSP_x`).
- Give labels in English and Spanish to new ontology terms and to problems, objectives and constraints, and a short comment in both languages to new ontology terms.
- Do not declare in the individuals files the properties of the ontology. Protégé does it as annotation properties when it cannot load the import, which takes the files out of OWL 2 DL; the catalogs described in [Imported modules](#imported-modules) prevent it.

### Problems
- A `Problem` is formulated by its `ProblemData` (input parameters, tables, matrices), its `DecisionVariable`s, at least one `Objective` and, optionally, `Constraint`s.
- Objectives and constraints are written as LaTeX expressions (`hasLatexExpression`); the quantities they use are identified by `hasLatexSymbol`. Use only the LaTeX described in the comment of `hasLatexExpression`, so that programs can evaluate the expressions:
  - indices start at 1, and each term of a subscript is an index: `d_{ij}` has two, so a product in an index is written `x_{2 \cdot i}`;
  - a column of a table is indexed by record (`v_i`) and a matrix by row and column (`d_{ij}`); values of decision variables can be indices (`X_{x_i}`);
  - constraints include the comparator and, if any, the quantifier (`x_i \leq 1 \quad \forall i \in \{1, \ldots, N\}`);
  - `\log` is the natural logarithm.
- Every quantity has a shape (`hasShape`: scalar, collection, matrix, table) and a value domain (`hasValueDomain`). Variables such as permutations or tables of data are then classified by the reasoner from their shape.

### Algorithms
- A `Metaheuristic` starts at a component (`hasStart`) connected to the others through `hasOutput`; its type (e.g. evolutionary algorithm) is inferred from the components it is connected to.
- Parameters are set through `ParameterValue` individuals (`hasParameter`, `hasType`, `hasValue`), and data structures have a shape and a value domain.
- `supportsShape` states the kind of solutions a metaheuristic or a component can handle.

### Shapes, value domains and sizes
- Shapes, value domains, sizes and bounds are named individuals, so they can be browsed and edited in Protégé.
- Reuse the predefined individuals when they fit, such as the value domains `UnitInterval` or `PositiveIntegers`, the literal values `Zero` and `One`, or `SolutionFirstDimensionSize` for sizes that depend on the solution. They are a starting point, not a closed list.
- Name the rest after the element they describe: `<subject>_shape`, `<subject>_domain`, `<domain>_lower`/`_upper`, `<shape>_length`/`_rows`/`_columns`, and `<parameter>_reference` for a reference to a parameter, shared by every size or bound that uses it.

## Imported modules
External vocabularies are reused as long as CO-META stays in OWL 2 DL. When a vocabulary is not in the OWL 2 DL profile, it is not imported as a whole: only the terms CO-META uses are extracted with [MIREOT](https://doi.org/10.3233/AO-2011-0087) (declaration, label and class hierarchy) into a module in `imports/`, which is imported by the ontology.

| Module | Source | Use |
|---|---|---|
| `imports/qudt.ttl` | [QUDT](https://qudt.org) 3.5.2, datatypes | Data shapes are subclasses of the QUDT structured datatypes (`qudt:Sequence`, `qudt:Set`, `qudt:Matrix`, `qudt:Table`...) |

The `catalog-v001.xml` files map the IRIs of the ontology and of its modules to the local files, so Protégé and the validation scripts use the working copy instead of the published version.

## Validation
Run `scripts/validate.sh` before committing changes. It requires Java 11+ and `pip install pyshacl`; ROBOT is downloaded on the first run. It checks that:

1. the ontology, its modules and its individuals are in the OWL 2 DL profile;
2. everything together is consistent and has no unsatisfiable classes (HermiT);
3. the tests in `tests/` give the expected result;
4. the individuals conform to the SHACL shapes in `SHACL/`.

The same checks run in GitHub Actions on every push and pull request, and must pass before the documentation is regenerated.

To add a test, create a Turtle file that imports `https://w3id.org/ontologies-ULL/CO-META` in the folder that states the expected result:

| Folder | Expected result |
|---|---|
| `tests/owl/inconsistent/` | The reasoner finds it inconsistent. |
| `tests/owl/consistent/` | It is consistent and conforms to the SHACL shapes. |
| `tests/owl/inferences/` | The SPARQL `ASK` query in the `.rq` file with the same name is true after reasoning. |
| `tests/shacl/invalid/` | It violates the SHACL shapes. |
